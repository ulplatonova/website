# CleanHub: сервер личного кабинета

Бэкенд для блока `lk/cleanhub-lk.html` (Тильда, `CHLK_CONFIG.mode='live'`). Node.js 22, **ноль внешних зависимостей**: только `node:http`, `node:sqlite`, `node:crypto`, `node:test` и встроенный `fetch`.

Что делает:

- вход и регистрация по SMS-коду или через Telegram-бота (без паролей), сессии на 30 дней;
- клиенты и заказы хранятся в Битрикс24 (контакты и сделки), локально только то, чего там нет: сессии, коды, реестр бонусов, реферальные коды, подписки;
- считает цены сам по `../pricing.js` (копия логики калькулятора сайта), цены с клиента игнорируются;
- бонусы и рефералы: уровни, кешбэк, списание до 30% заказа, возврат при отмене, награда за друга;
- подписки на поддерживающую уборку: график визитов и автоматическое создание сделок на ближайшие визиты;
- уведомления о статусах заказа в Telegram;
- подготовленный (но не проверенный) приём оплаты подписки через ЮKassa.

Контракт API: [CONTRACT.md](./CONTRACT.md). Проверка здоровья: `GET /health` отвечает `{"ok":true}`.

## Быстрый старт

```bash
cd lk/server
cp .env.example .env        # заполните BITRIX_WEBHOOK_URL и остальное
export $(grep -v '^#' .env | xargs)   # или задайте переменные любым удобным способом
npm run setup:bitrix -- --dry-run     # посмотреть, какие поля создадутся в Битриксе
npm run setup:bitrix                  # создать поля
npm start
npm test                              # сквозные тесты на эмуляторах, без интернета
```

Нужен Node.js 22.13 или новее (`node:sqlite`). Node может печатать `ExperimentalWarning: SQLite is an experimental feature`, это нормально.

Без `BITRIX_WEBHOOK_URL` сервер не запустится и напишет, что именно нужно указать (исключение: `NODE_ENV=test`).

Docker (контекст сборки — каталог `lk/`, потому что нужен `pricing.js`):

```bash
docker build -f server/Dockerfile -t cleanhub-lk lk/
docker run -d --name cleanhub-lk --env-file server/.env -p 8080:8080 -v cleanhub-lk-data:/data cleanhub-lk
```

Образ `node:22-alpine`, процесс под пользователем `node`, `HEALTHCHECK` по `GET /health`, база в томе `/data`.

## Настройка Битрикс24

1. **Входящий вебхук.** Разработчикам → Другое → Входящий вебхук. Право: **CRM** (crm). Скопируйте адрес вида `https://<портал>.bitrix24.ru/rest/<id>/<токен>/` в `BITRIX_WEBHOOK_URL`. Токен вебхука равен ключу доступа: не публикуйте его.
2. **Пользовательские поля.** Запустите `npm run setup:bitrix` (сначала с `--dry-run`). Скрипт создаёт через `crm.deal.userfield.add` поля сделки `UF_CRM_CH_SERVICE`, `_TARIFF`, `_AREA`, `_ADDRESS`, `_SLOT`, `_VISIT_DATE`, `_BONUS_SPENT`, `_EXTRAS`, `_SUB_ID` и через `crm.contact.userfield.add` поле контакта `UF_CRM_CH_REFCODE`. Существующие поля пропускаются, повторный запуск безопасен. Если поле не создано, Битрикс молча отбросит значение, поэтому не пропускайте этот шаг.
3. **Воронка и стадии.** Если заказы идут не в основную воронку, задайте `BITRIX_CATEGORY_ID` и `BITRIX_STAGE_NEW` (например, `C2:NEW`). `BITRIX_WORK_STAGES` — стадии, которые клиент видит как «в работе»; сравнение идёт по части после `:`, поэтому `C2:EXECUTING` и `EXECUTING` одинаковы. Успех и провал определяются семантикой стадии Битрикса (`S` и `F`), а не названием.
4. **Исходящий вебхук.** Разработчикам → Другое → Исходящий вебхук. Обработчик: `https://<ваш API>/bitrix/events`. События: `ONCRMDEALUPDATE` и `ONCRMDEALADD`. Скопируйте выданный **токен приложения** в `BITRIX_EVENT_TOKEN`. Сервер сверяет его timing-safe, при несовпадении отвечает 403.
5. Бонусы дублируются сверкой: при каждом `GET /me` и `GET /orders` сервер обрабатывает все завершённые сделки клиента, поэтому пропущенное событие вебхука ничего не ломает.

## Telegram-бот

1. В @BotFather: `/newbot`, получите токен → `TELEGRAM_BOT_TOKEN`, имя бота без `@` → `TELEGRAM_BOT_USERNAME`.
2. Придумайте секрет (A-Z, a-z, 0-9, `_`, `-`) → `TELEGRAM_WEBHOOK_SECRET`.
3. Зарегистрируйте вебхук (один раз, с HTTPS-адресом):
   ```bash
   curl -sS "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/setWebhook" \
     --data-urlencode "url=https://<ваш API>/telegram/webhook" \
     --data-urlencode "secret_token=$TELEGRAM_WEBHOOK_SECRET"
   ```
4. Сервер принимает только запросы с заголовком `X-Telegram-Bot-Api-Secret-Token`, равным секрету. Токены привязки и входа одноразовые и живут 10 минут.

## SMS

- `console` — код печатается в лог. **Только для разработки**, в продакшене не используйте.
- `smsru` — запрос `GET https://sms.ru/sms/send?api_id=…&to=7XXXXXXXXXX&msg=…&json=1`, успехом считается `status_code: 100`. **Провайдер написан по документации sms.ru и не проверялся на живом сервисе.** Перед запуском отправьте тестовое SMS на свой номер.
- `memory` — для тестов, коды читаются из памяти процесса.

Защита: код 4 цифры, хранится хэшем, живёт 5 минут, 5 попыток; лимиты: 1 код в 60 с и 5 в час на номер, 20 в час на IP; ответ `/auth/code` одинаков для известных и неизвестных номеров.

## Подписки и материализация

Сервер раз в `MATERIALIZE_INTERVAL_MIN` минут создаёт сделки на визиты активных подписок в окне «сегодня + 7 дней». Повторный запуск дублей не создаёт (`UNIQUE(sub_id, date)` в `sub_visits`).

Запасной вариант без внутреннего таймера (`MATERIALIZE_INTERVAL_MIN=0`) — cron:

```cron
5 * * * * cd /opt/cleanhub/lk/server && ADMIN_KEY=… PORT=8080 node scripts/materialize.js >> /var/log/cleanhub-materialize.log 2>&1
```

или `curl -X POST -H "X-Admin-Key: $ADMIN_KEY" https://<ваш API>/internal/materialize` (необязательное поле `daysAhead`, 0–60).

## Развёртывание

- **HTTPS обязателен.** Поставьте перед сервером nginx/Caddy с сертификатом, включите `TRUST_PROXY=1` (прокси должен добавлять реальный IP последним в `X-Forwarded-For`). Сам сервер слушает обычный HTTP.
- **Резервные копии.** Вся локальная информация лежит в файле `DB_PATH` (режим WAL, рядом файлы `-wal` и `-shm`). Делайте копии через `sqlite3 lk.sqlite ".backup 'backup.sqlite'"` или копируйте все три файла при остановленном сервере. Потеря реестра бонусов = потеря баланса клиентов (Битрикс хранит только сделки).
- Один экземпляр сервера на одну базу SQLite. Горизонтальное масштабирование не предусмотрено.
- Останов по `SIGTERM`/`SIGINT` корректный: закрывается HTTP и база.
- Секреты только в окружении. В логи не попадают коды, токены и ключи.

## Что проверено и что нет

Проверено (автотесты `npm test`, 47 проверок на эмуляторах Битрикс24 и Telegram, SMS-провайдер `memory`):

- вход и регистрация по SMS, отсутствие перебора номеров, лимиты, неверные коды, срок жизни кода;
- реферальная программа: по 500 бонусов ровно один раз, в том числе при повторных и параллельных событиях;
- список заказов из сделок: статусы, суффикс стадии (`C2:WON`), позиции из товарных строк;
- создание заказа: серверный пересчёт цены, лимит 30% и баланс, поля сделки, товарные позиции, списание бонусов, защита от гонки, возврат при отмене;
- уровни лояльности; подписки: создание, даты визитов для 2 и 4 раз в месяц, материализация (однократная), пауза, отмена, чужие и поддельные id;
- привязка Telegram, вход через бота, уведомления о статусе (один раз на статус), отключение уведомлений;
- 403 при неверном токене события Битрикса, CORS preflight, 401 без токена, скрипт `bitrix-setup` (dry-run и идемпотентность).

**НЕ проверено на реальных сервисах:**

- живой Битрикс24 (эмулятор написан по документации методов; реальные ответы, лимиты и права могут отличаться);
- sms.ru;
- Telegram Bot API (реальные вебхуки и доставка);
- ЮKassa (адаптер `payments.js` не запускался ни разу против настоящего API).

Перед боевым запуском пройдите сценарии вручную на тестовом портале Битрикс24, со своим номером телефона и тестовым ботом.

## Оплата подписки (ЮKassa) — ограничения

Адаптер включается `PAYMENTS_PROVIDER=yookassa`, **не проверен на реальном API**. Создаётся платёж на сумму `perMonth` (первый месяц) с `save_payment_method`, вебхук `/yookassa/webhook` не доверяет телу и перепроверяет платёж запросом `GET /v3/payments/{id}`, дополнительно сверяя привязку к подписке и сумму. Не реализованы: чек по 54-ФЗ (`receipt`), рекуррентные списания следующих месяцев, возвраты. Без этого включать оплату в продакшене нельзя.

## Deviations (отклонения от контракта и принятые решения)

1. `order.total` равен сумме к оплате (`OPPORTUNITY` = цена минус бонусы), как в демо-версии кабинета; цена до бонусов = `total + bonusSpent`. Контракт прямо не уточняет.
2. В сделку добавлен `IS_MANUAL_OPPORTUNITY='Y'`, иначе Битрикс пересчитывает сумму сделки по товарным позициям и теряет вычет бонусов.
3. Возврат бонусов по проигранной сделке делается по записи реестра `deal:<id>:spend`, а не по полю `UF_CRM_CH_BONUS_SPENT`: поле в Битриксе может поправить менеджер, реестру доверяем больше.
4. Уровень для кешбэка считается по сумме выполненных сделок клиента с меньшим номером, чем у обрабатываемой («до этой сделки»).
5. События Битрикса обрабатываются синхронно (до 8 с) и только потом возвращается 200; при ошибках тоже 200, расхождения лечит сверка в `/me` и `/orders`.
6. Токен сессии, выданный при входе через Telegram, лежит в таблице `tg_tokens` до первого опроса `/auth/telegram/status` (отдаётся один раз и удаляется, срок 10 минут). Неизвестный или просроченный токен входа даёт 404.
7. `GET /telegram/status?token=` возвращает состояние привязки авторизованного клиента; токен только проверяется на формат.
8. Допуслуги (`extras`) в подписке игнорируются: цена подписки фиксирована по `pricing.subscription`.
9. Статус `finished` у подписки выставляется по дате окончания (при чтении и при материализации).
10. Телефон: российский номер из 10 цифр после `+7`, первая цифра 3–9. Принимаются `+7`, `7`, `8`, пробелы, скобки, дефисы.
11. Если `TELEGRAM_WEBHOOK_SECRET` или `BITRIX_EVENT_TOKEN` не заданы, соответствующие вебхуки отвечают 403 (закрыто по умолчанию).
12. Добавлены переменные, которых нет в контракте: `CABINET_URL`, `SITE_URL`, `TRUST_PROXY`, `LOG_LEVEL`, `BITRIX_RETRY_BASE_MS`, `BITRIX_FIELD_*`, `*_API_BASE`.
13. Добавлено: `scripts/materialize.js` (для cron), необязательный `daysAhead` у `/internal/materialize`, лимит 10 действующих подписок на клиента, лимит попыток промокода (20 в час).
14. Статус приглашённого `ordered` ставится, когда у него есть любая не проигранная сделка, известная серверу.
15. Если не удалось записать товарные позиции после создания сделки, заказ не отменяется (сделка уже в CRM), ошибка пишется в лог; в списке заказов позиции восстанавливаются из полей сделки.
